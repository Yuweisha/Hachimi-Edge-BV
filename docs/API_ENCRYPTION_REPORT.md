## 0. 方法论（重要）

| 类型 | 本报告做了什么 | 可靠性 |
|---|---|---|
| **静态反汇编** | capstone 反汇编 `libnative.dll`；`.pdata` 解析函数边界；字符串交叉引用定位 mbedTLS 函数 | 指令级可信，但「这段代码是否被执行」静态不可知 |

| **运行时验证** | hook 关键函数抓输入输出，Python 独立复算并逐字节比对 | 最强，但依赖 hook 点选对 |

**核心教训**：本项目多次因「静态看到某段代码」就下结论而走弯路（见第 8 节）。所有最终结论都经过运行时逐字节验证。

## 1. 结论摘要

```
msgpack 明文
  → LZ4 压缩
  → AES-128-CTR 流加密
  → base64
  → TLS 1.3（外层）
```

算法、密钥流、KDF、封装格式全部验证通过。

**密钥由 P-256 ECDH 协商产生：`Z = d × Q`（d 是每次随机的客户端私钥，Q 是硬编码的服务器公钥）。**

服务器要复算 key，必须有 `d` 或 `Z`，两者都只在客户端内存里。

且请求与响应使用不同的 AES 上下文（`setkey` 每请求被调 6 次），这也是请求解密失败的独立原因。

## 2. 对称算法层（完全验证）

### 2.1 密钥流

```
ks[i] = AES-128-ECB( key, IV12 ‖ BE32(ctr0 + i) )
```

- `IV12` 从 `ctx + 0x180` 前 12 字节
- `ctr` 从 `ctx + 0x180` 后 4 字节**大端**读取
- 每块 `ctr` +1
- 算法本体在 `libnative+0x43B70`（AES 分派）

### 2.2 验证证据

```
key  = 3D7E321F99F5E497BA9FA1884F1A6A1A
iv16 = 84F5B7F191DDBE393B409A749ACE49BD   (IV12 ‖ ctr0=9ACE49BD)
```

| 输入块 | 客户端输出 | Python 复算 | 结果 |
|---|---|---|---|
| `00…00` | `769AA67762F0927486A80BB6FAD327A5` | 同 | ✓ |
| `84F5B7F1…9ACE49BD` | `12631DB71969DC2BCB74A83E5404A655` | 同 | ✓ |

后续块 `9ACE49BE/BF/C0` 的密钥流也按预期递增。

**结论：AES-128-ECB + CTR 构造无歧义。**

### 3.1 完整公式

```
R1  = MD5( S1[16] ‖ S2[16] ‖ S3[16] )              → 16 字节
key = MD5( X[16]  ‖ Y[32]  ‖ R1[16] ‖ S6[20] )      → 16 字节
```

## 4. 明文布局（实测）

```
偏移    长度   内容
0x00     4     明文总长度 LE32
0x04    32     服务器公钥（编译期常量）
0x24    20     S6 —— 证书指纹类字段
0x38    16     S1
0x48    16     S3
0x58    66     混合段（含设备/会话标识）
0x9A    16     S2
0xAA     …     msgpack body
```

`S1`/`S2`/`S3`/`S6` 全部在明文里，服务器可读。

`0x04` 处 32 字节是**服务端公钥**，来自 `LibNative.Network.CommonHeader()` 的硬编码常量（`new byte[52] {…}`，前 32 公钥 + 后 20 证书指纹），源码已确认。

## 6. 请求与响应使用不同的 key（决定性发现）

`hook setkey`（`0x143E0`）实测被调用 **6 次**，每次 ctx 都不同：

```
[setkey #0] ctx=0x13E230
[setkey #1] ctx=0x13E430
[setkey #2] ctx=0x13E1D0
[setkey #3] ctx=0x13E430
[setkey #4] ctx=0x13DBE0
[setkey #5] ctx=0x13E430
```

**这就是为什么「请求加密阶段抓到的 key」解不开客户端请求，而加密响应却能成功：**

- 响应方向：服务器用上报的 key 加密 → 客户端能解 ✓（已验证）
- 请求方向：客户端用的是另一把 key → 服务器解不开 ✗

## 7. 更正：`0xE180` 是 API 层的 P-256 ECDH（推翻旧结论）

### 7.1 决定性证据链

**① `0x10F0` 不是 LZ4 压缩，是请求加密主控**

hook 在 `0x10F0` 上的 `[cmp]` 日志显示它在解析明文头：

```asm
0x1131: movzx ecx, byte [rcx+3]   ; buf[3]
0x1157: add   ecx, 4              ; 长度 + 4
0x115A: cmp   ecx, 0x78           ; >= 120 ?
0x116D: lea   rax, [rsi+0x24]     ; buf+36 = 跳过「长度4+公钥32」
0x1175: cmp   ecx, 0xaa           ; == 170 ?
```

`buf+0x24` 正好是 S6（20 字节指纹）的起点。LZ4 压缩函数不该做这些。

**② `0x10F0` 内部调 ECDH**

```asm
0x1727: call 0xFED0      ; ECDH 准备（内含 0x10001 = RSA 常量，见下）
0x1766: call 0xED20      ; ECDH 相关（169 B）
0x17A5: call 0xE180      ; ECDH 核心（pbits=384 分支）
```

参数统一：`rcx = rbp-0x50`（ECDH ctx），`rdx = rbp+0x80`（输出）

**③ `Y` 是 P-256 x 坐标的字节序反转（已用两组样本验证）**

`0x16310`（`mpi_write_le`）把 mpi 按小端写成 32 字节，代码随后整段反转：

```
wmpi 输出 = 6A3AA534...178D16（小端）
反转后    = 168D17FF...A53A6A
md5#4（Y）= 168D17FF...A53A6A   ✓ 完全匹配
```

**④ 反转后的 Z 是合法的 P-256 点坐标**

```python
Y = 9C46B04DED98AB73FC03B1AC8E77EBACAF0B8D6A8A8026895EA59DC671EBE858
Z = Y[::-1]   # 58E8EB71C69DA55E8926808A6A8D0BAFACEB778EACB103FC73AB98ED4DB0469C

secp256r1 解析：
  Z + 0x02 前缀 → 在曲线上 ✓
  Z + 0x03 前缀 → 在曲线上 ✓
  Y 原样 + 前缀 → 失败 ✗
```

**只有反转后的 Z 在曲线上，Y 原样不在。** 这确认了字节序。

### 7.2 服务器公钥 `5AEB...` 也是 P-256

```
5AEBF09DCC92BBB819C891356A114A3E98E62CC7FA9E1FE0A3CD06537EA5F388

原始 + 0x02/0x03/0x04 前缀 → 全部失败
反转 + 0x02 前缀         → 在曲线上 ✓
反转 + 0x03 前缀         → 在曲线上 ✓
```

与 Z 一样：**只有反转后才在曲线上。**

（注：0x02 与 0x03 同时通过只说明「该 x 在曲线上有解」，概率约 50%，单独不足以证明。但与 Z 的表现一致，加上 `0x10F0` 里的 ECDH 调用，证据链成立。）

### 7.3 正确的加密链路（修正版）

```
请求加密主控 0x10F0
  ├─ 解析明文头（长度 / 公钥 / S6）
  ├─ P-256 ECDH(客户端私钥 d, 服务器公钥 Q) → 共享密钥 Z (32B)
  ├─ Y = reverse(Z)
  ├─ X = ??? (16B, 未知)
  ├─ R1 = MD5(S1 ‖ S2 ‖ S3)
  ├─ key = MD5(X ‖ Y ‖ R1 ‖ S6)
  └─ 用 key 做 AES-128-CTR 加密 body
```

### 7.4 命名澄清（重要，避免误解）

之前文档里的 `X`/`Y` **不是椭圆曲线的坐标**，只是两个相邻栈缓冲区的临时名字：

| 旧名 | 真实含义 | 与 EC 的关系 |
|---|---|---|
| `Y[32]` | `reverse(P-256 共享密钥 x 坐标)` | **是 EC 变量** |
| `X[16]` | **未知**，16 字节 | **不是 EC 变量**（P-256 输出必定 32 字节） |

建议后续改用 `ecdh_z`（32B）和 `unknown16`（16B），避免与曲线的 X/Y 坐标混淆。

### 7.5 关于旧结论「`0xE180` 是 TLS」

这个结论**是错的**。当时的依据是：`pbits=384` + 「libnative 内嵌 mbedTLS 用于 TLS」。

但 `0xE180` 在 `0x10F0`（请求加密主控）里被调用，而 `0x10F0` 处理的是 API 请求体。所以它是 **API 层的 ECDH**，不是 TLS。

`pbits=384` 可能是多曲线支持的分支（同一函数处理 P-256/P-384），实际走哪条由 ctx 决定。

| 错误结论 | 实际情况 | 代价 |
|---|---|---|

## 9. 服务器端加密已落地

`Hachimi-Edge/tools/game_crypto.py` + `local_server.py`：

```python
def pack_resp(declared, plain, path=""):
    key, iv16 = get_session_crypto(path)
    if key:
        return encrypt_body(plain, key, iv16[:12], BE32(iv16[12:]))
    return LE32(declared) + b"\x00"*32 + plain   # 无 key 回落明文
```

实测响应能被上报的 key 解开：

```
load/index 响应 3,659,724 B (base64)
  → 2,744,791 B，密文区非零 2,734,130
  → 解密后 msgpack 解析成功
  → data 键: common_define / user_info / tp_info / rp_info / coin_info / trained_chara …
```

插件侧通过 WinHTTP 上报 `(sid, key, iv, path)`，**每请求一次**（IV 每请求都变，只报一次会错）。

关键实现细节：
- `WinHttpOpen` 必须用 `WINHTTP_ACCESS_TYPE_NO_PROXY`（1），否则被残留系统代理卡死（`OS Error 12029`）
- headers 必须以 `\r\n\r\n` 结尾
- 必须显式设置 `SECURITY_FLAG_IGNORE_ALL` 才能连自签证书
- URL 解析要同时支持 `http://` 和 `https://`（早期只认 https，本地调试静默失败）

## 10. 未解决 / 不可行

### 10.1 服务器独立解密请求（不可行）

需要 ECDH 另一端私钥（客户端或 Cygames 服务器的），两者都拿不到。

**这不是研究没做完，是密码学设计本身禁止的。**

### 10.2 `X[16]` 的来源（唯一阻塞项）

```
Y[32]  = reverse(Z)，Z = P-256 ECDH 共享密钥   ✓ 已确认
X[16]  = 未知                                   ✗
```

已排除：
- 不是 Z / Y / 盐 / S1 / S2 / S3 / S6 的任何哈希（试遍 8 个单元素 × 3 种算法 + 112 种两两组合）
- 不是 P-256 输出（P-256 输出必为 32 字节，X 只有 16 字节）

最可能：`X = MD5(客户端私钥)`。若成立，则服务器永远无法复算 —— 与现有现象完全吻合。

验证方法：枚举私钥 `d`，算 `Z' = d × Q`，比对实测 Y；同时算 `MD5(d)` 比对 X。

> 注：高人提过「种子空间有效值是 2^33」，若私钥由 33 位种子派生，约 86 亿次枚举在 GPU 上数小时可完成。

### 10.2-bis 命名澄清

`X`/`Y` 是相邻栈缓冲区的临时名字，**与椭圆曲线的 X/Y 坐标无关**：

| 旧名 | 真实含义 | 与 EC 关系 |
|---|---|---|
| `Y[32]` | `reverse(P-256 共享密钥)` | 是 EC 变量 |
| `X[16]` | 未知 16 字节 | 不是 EC 变量 |

建议后续用 `ecdh_z` 和 `unknown16`。

### 10.3 其他

- `0x58 ~ 0x9A` 的 66 字节字段边界未最终确定
- 32 字节响应头实测为随机 nonce（同 SID 两次请求完全不同）

## 12. 结论

内层加密已可完整复现：给定 `key`、`IV12`、`ctr0`，任何 AES-128-CTR 实现都能生成客户端接受的加密体。

**但这三者只能从客户端取得**（`X`/`Y` 是内存内的临时中间值）。

要脱离插件自主加密，还需定位 `X`/`Y` 的生成点 —— 现有证据表明它们与 TLS 无关、与已 hook 的 ECDH 无关，是客户端自有的协商逻辑。
