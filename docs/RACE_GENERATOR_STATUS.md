# 比赛剧本生成器 — 现状说明

> 本文档只写**已通过实际运行或逐字节验证**的内容。所有未验证、未实现、已知会出错的地方都在「缺陷」章节单独列出。
> 最后更新：2026-10-28

---

## 一、整体架构

```
race_entry   （进场马匹数据）
      ↓
race_start   （race_scenario 剧本：帧数据 + 结果块 + 事件区）
      ↓
客户端纯播放，不做任何计算
```

**核心结论：客户端是纯播放器。** 名次、用时、马身、跑位全部来自 `race_scenario` 里的数据，客户端只负责渲染。这一点通过逐字段替换实验确认——改剧本字段，画面结果跟着变；不改，就是模板值。

服务器端相关文件：

| 文件 | 作用 |
|---|---|
| `tools/db_race_entry.py` | 生成 `race_entry` 响应的马匹数据 |
| `tools/db_race_start.py` | 生成 `race_start` 响应的剧本（调下面两个之一） |
| `uma_replay/gen_race_real.py` | 真实解包模型，零模板生成帧数据 |
| `uma_replay/gen_race_full.py` | 模板改造路线（保留模板帧结构，替换数值） |
| `uma_replay/gen_events.py` | 事件区生成（从模板过滤马索引） |
| `tools/db_practice_race.py` | 练习赛（`practice_race/race_start`） |
| `uma_replay/race_profiles.json` | 21 种距离的赛道参数 |

## 二、剧本二进制格式（已逐字节验证）

### 2.1 头部

```
偏移    类型    含义
0x00    u32     version
0x04    u32     simVersion
0x08    u32     seed
0x0C    u32     charaNum        马匹数量
0x10    u32     charaSize       每匹马每帧的字节数，固定 12
0x14    u32     (保留，固定 0)
0x18    u32     frameNum        帧数
0x1C    u32     frameBytes      4 + charaNum × 12
```

### 2.2 帧区

从 `0x20` 开始，共 `frameNum × frameBytes` 字节。

```
每帧：[u32/f32 Time] + charaNum × 12 字节
每匹马 12 字节：
  +0x00  f32   Distance   已跑距离（米）
  +0x04  u16   Speed      速度（需确认缩放，见缺陷 §5.1）
  +0x06  u16   Hp         剩余体力
  +0x08  u16   BlockFront 固定 0xFF00
  +0x0A  u8    f3
  +0x0B  u8    f4
```

**注**：`LanePos`（横向跑道位置）在 12 字节中的确切偏移尚未逐字节确认，目前实现里按 `i × 555` 填充（见缺陷 §5.2）。

### 2.3 结果区

帧区之后：

```
+0x00                       u32  固定 0
+0x04                       u32 × (charaNum+1)  变长结果块的长度数组
之后                        结果块 × charaNum
```

**单个结果块的格式（固定 39 字节 + n×5 字节技能）：**

```
+0x00  i32    FinishOrder             名次（0-based）
+0x04  f32    FinishTime              完赛时间
+0x08  f32    FinishDiffTime          与前一名的差（马身 = diff × 60000 / 9000）
+0x0C  f32    (未命名，疑为 +0x18)
+0x10  f32    startDelay              起跑延迟
+0x14  u8     gutsOrder               按 guts 的排名
+0x15  u8     wizOrder                按 wiz 的排名
+0x16  f32    lastSpurtStartDistance  末脚开始距离
+0x1A  u8     (未命名，疑为 +0x30)
+0x1B  i32    defeatType              失败类型
+0x1F  f32    runUpTime               （未完全确认）
+0x23  f32    (未命名，疑为 +0x20)
+0x27  i32    skillCount              技能条数 n
+0x2B  n × 5B 技能块                  ← 见缺陷 §5.3
```

### 2.4 事件区

结果区之后：

```
u32                      记录数
重复 N 次：
  u16  长度
  变长数据
```

事件区承载技能发动镜头的时机、BGM 切换点、换道距离。**空事件区（记录数=0）会导致「观看比赛」卡在赛场加载**——这一条是实测结论。

## 三、已验证的机制

### 3.1 决定名次的字段

**`FinishOrder`（结果块 +0x00，int32，0-based）是唯一决定名次的字段。**

写过 float 位模式进去会被判非法、静默回退模板值，表现为「改什么都没用」。这是踩过的坑。

### 3.2 决定用时的字段

`FinishTime`（+0x04）决定显示用时。帧数据里的 `Distance` 只影响画面跑位，不影响成绩显示。

### 3.3 决定马身的字段

`FinishDiffTime`（+0x08）→ 马身 = `diff × 60000 / 9000`（1 马身 ≈ 0.15 秒）。

属性接近时相邻名次可能只差 0.004 秒，画面上粘在一起。当前实现给相邻名次设了 0.13 秒（约 0.87 马身）下限。

### 3.4 帧数与时间轴

**`frameNum` 不能随意改。** 必须与模板一致（京都 3200m 为 193 或按 `t_ref` 精确推导），否则客户端判非法。

时间轴是「先密后疏」：前约 41 帧按 15fps，之后按 `DT_SPARSE`。

**关键坑**：生成帧用的时间轴和写帧时间戳必须是**同一个数组**。曾经用过两套（`build_frames` 内部均分、`build_real` 自己算疏密），导致 11 秒的距离被贴成 0.667 秒的时间戳，隐含速度 240 m/s，画面马匹瞬移、全部重叠穿模。

### 3.5 `t_ref` 是展示时间，不是实际时长

`race_course_set.finish_time_min/max` 里的值是**展示时间**，已含 ×1.18 系数。实际比赛时长 = `t_ref / 1.18`。

曾把方向搞反（写成 `t_ref × 1.055`），导致剧本拉到 165 秒而马 124 秒就跑完，最后 40 秒所有马钉在终点线上重叠。

当前实现：`t_end = min(最慢马时间, t_ref / 1.18) × 0.98`。

### 3.6 距离必须查表

```
ultimate_race_contents → race_instance → race → race_course_set
```
全游戏共 **21 种距离**：1000/1150/1200/1300/1400/1500/1600/1700/1800/1900/2000/2100/2200/2300/2400/2500/2600/3000/3200/3400/3600。

场地：`ground=1` 草地（2175 场）、`ground=2` 泥地（749 场）。

### 3.7 已跑通的组合

| 赛道 | 距离 | 结果 |
|---|---|---|
| 京都 | 3200m | 能加载、能播、名次与用时正确 |
| 中山 | 2500m | 能加载（事件区坐标有偏差，见 §5.4） |

练习赛：`ri=511301` 18 匹 3200m、`ri=680421` 14 匹 1600m，均能生成。

## 四、速度模型

来自社区解包（NGA 贴 + 配套 Excel 计算器），**不是自行拟合**。

```
v0    = 20 - (distance - 2000) / 1000
v1/v2 = (style_v[i] + wiz·log10(wiz/10)/550000 - 0.00325) × v0
v3    = (style_v[2] + 同式) × v0 + √(speed/500) × dist_proper_v
v4    = (style_v[2] + 0.01) × v0 + √(speed/500) × dist_proper_v

a0 = 24 + 0.0006·√(500·power)·style_pow[0]·ground_proper·dist_proper_a
a1/a2/a3 同结构，无常数项

HP       = distance + 0.8·stamina·style_hp
HP终盘系数 = 1 + 200/√(600·guts)
巡航消耗   = 20·coef·(v-v0+12)² / 12² · t
加速消耗   = 20·coef·[(at+v-v0+12)³ - (v-v0+12)³] / (12²·3a)
d_lastspurt = min(HP估算, distance/3)
赛程分段    前 1/6 / 中间 1/2 / 后 1/3
```

注意：`√(速度/500)` 而非 `√(速度/5)`——前者是社区原文，后者是流传的笔误（差 10 倍，4.5 m/s vs 0.45 m/s）。

**这份模型是本项目唯一验证过的速度来源。自行拟合的 `cruise = K·speed^0.066` 会把 2000m 算成 201 秒（实际 97.87 秒），偏差近一倍。**

## 五、缺陷清单（真实存在，未修复）

### 5.1 `Speed` / `Hp` 字段的缩放未确认

帧里 `Speed` 是 u16，实际是「米/秒 × 100」还是别的缩放，**没有逐字节验证过**。目前按 `×100` 写入，画面速度看起来合理，但没有对照过客户端内部读取的值。

影响：速度显示可能有细微偏差，不影响名次。

### 5.2 `LanePos` 是固定值，不是真实换道

当前实现：`LanePos = i × 555`（第 i 匹马）。

模板里的实际数据是**动态的**：起跑 0/555/1111/1666…（17 匹到 9222），之后逐渐向内收敛到 461~5987。这是赛道几何造成的（直道散开、弯道收拢），不是换道逻辑。

影响：所有马全程平行排列，没有横向移动。不会导致穿模（横向仍是分开的），但视觉上比真赛单调。

### 5.3 技能块是空的

结果块末尾的 `skillCount + n×5 字节` 目前写 0 条。

**这意味着比赛里不会有任何技能发动。** 线上比赛会看到「末脚」「差し切り」之类的技能演出、镜头切换、以及技能对速度的实时影响——这些现在完全没有。

技能块的 5 字节结构也**未解析**（可能是 `skillId(u16) + 发动距离(u16) + 标志(u8)`，但没有验证）。

### 5.4 事件区是从模板过滤来的，坐标不匹配

`gen_events.py` 的做法：从京都 3200m 模板取 348 条事件，按 `charaNum` 过滤掉索引越界的（17 匹→16 匹丢了 9 条），保留 339 条。

**问题**：事件里的时间/距离坐标是京都 3200m 的。跑中山 2500m 时，技能镜头时机、BGM 切换点、换道位置全部错位。

影响：能播，但演出节奏不对。跑京都 3200m 时基本正确（因为同赛道）。

### 5.5 Hachimi 读不到比赛进度条

Hachimi 本体（`cri_mana_vpx.dll`）在比赛中有一些依赖比赛状态的功能，当前**读不到比赛的进度条数据**。

具体表现：比赛播放过程中的状态栏信息不完整/不更新。

原因未定位——可能是 Hachimi 期望的某个字段在剧本里没有被正确填充，也可能是它走的是另一套状态源（`Gallop.UltimateRace*` 的某个属性），而我们的响应里那部分还是模板值。

**这是已知未解决项，不是配置问题。**

### 5.6 玩家位选角靠猜

客户端选角色时**不发任何网络请求**（`race_entry` / `race_start` 的请求体里只有公共头：`device_id` / `viewer_id` / `steam_id`，没有 `trained_chara_id`）。

所以服务器不知道玩家选了谁。当前实现：

1. 优先用请求里带的 `trained_chara_id`（实际永远为 None）
2. 回退到 `load/index` 响应的 `trained_chara_array` 按策略挑（最近创建 / rank 最高）
3. 再回退到模板角色（金花 `chara_id 1114`，固定第 4 位）

**影响**：玩家位可能显示的不是自己选的角色，名次也固定。曾把 `last_race_ctx.json` 里的旧值（`chara=470` 迷人景致）误当成玩家选择。

### 5.7 末尾几帧可能全在终点

如果所有马在 `t_end` 之前就冲完线，最后几帧的距离全部等于赛道长度，画面上所有马叠在终点线上。

当前用 `t_end = min(最慢马, t_ref/1.18) × 0.98` 缓解，但**没有彻底解决**——属性差异很小时（速度差 5%），仍可能出现。

实测：真实属性差距（玩家 speed 2000 / NPC 1700~800）时帧跨度 66~166 米，正常；温和差距（speed 1200~1650）时末尾多帧全为 0 跨度。

### 5.8 只有部分距离×场地组合实测过

`race_profiles.json` 里 21 种距离都有参数，但**实际跑通过画面的只有京都 3200m 和中山 2500m**。

其余组合只验证了「剧本能生成、结构完整」，没有验证「客户端能加载、能播放、名次正确」。

### 5.9 与线上版还差的四项

| 项 | 状态 |
|---|---|
| 技能发动 | 完全没做（见 §5.3） |
| 人气 / 三印记 | 显示值是模板的，没有按实际计算 |
| `reflect_item_effect` | 已动态化，但**没有实测过**道具生效 |
| 结算持久化 | 没做，比赛结果不写回数据库 |

### 5.10 另外两个已知问题

- **`daily_race/index` 软死**：真实响应从未录到，接口返回的是构造数据。
- **181 张卡上限**：客户端缺 bundle 资源，往 `load/index` 里加第 182 张卡会崩在 60%。

## 七、结论

**能做的**：给定马匹属性、赛道距离、场地，生成一份客户端能加载、能播放、名次用时正确、画面上马匹前后拉开距离的比赛剧本。已覆盖 21 种距离的参数生成，其中 2 个组合实机验证过。

**不能做的**：技能发动、真实换道、事件演出与赛道精确匹配、玩家选角、结算持久化。

**核心风险**：所有「客户端能加载」的结论都建立在「结构和模板一致」这个前提上。一旦 `frameNum`、`charaNum`、结果块长度中的任何一项偏离模板的规律，客户端会静默判非法并卡加载——而且不报错。
