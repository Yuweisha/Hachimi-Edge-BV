# 台服踩坑报告 vs 本项目发现的对照

> 对照对象：《132 — 本地服务端踩坑总账：SID 是什么、218 从哪来、每种错误怎么造成又怎么解决》
> 来源：合作方提供的台服逆向笔记
> 本文只做**对照**，区分「双方一致」「双方矛盾」「只有对方有」「只有我们有」四类。

---

## 一、双方一致的（可以直接互相印证）

| 项 | 台服 | 本项目 |
|---|---|---|
| 响应外层结构 | `base64 → LE32(n) + 32B salt → 密文` | **完全相同**（我们记作 `[u32][32B 头][密文]`） |
| LZ4 位置 | 解密后是 LZ4 帧 | **相同**（`LibNative.LZ4.SimpleLZ4Frame`） |
| 前 36 字节客户端丢弃 | `Array::Copy(raw, 0x24, …)` | 我们伪造时写 0 即可，**行为一致** |
| 32 字节 salt 不参与密钥派生 | 明确写了 | 我们此前也验证过 32B 头与已知 key/IV 无关 |
| 会话失效的后果 | `result_code=218`「在其他设备登入」 | 我们遇到过（会话不同步） |
| `servertime` 要沿用真实值 | 日界 05:00 | **相同**（我们的 `data_headers.servertime` 刷新逻辑） |

## 二、双方矛盾的（需要重新验证）

### 2.1 LE32 字段的含义

| | 定义 |
|---|---|
| 台服 | `n = 32`，**49 个响应全部为 32**，视为固定头长度标记 |
| 本项目 | 视为**明文长度**（我们记录的各种值：397、1042、2744740 等） |

**这是最需要修正的一条。**

台服实测「49 个捕获响应全部 `n=32`」，如果这是真的，那我们把它当明文长度的做法就是错的。

**但**：我们自己抓的数据里，`[res #N] 注入 526 B declared=526` 这种日志说明 `declared` 是变化的，且与注入长度一致。

**可能的解释**（未验证）：
- 台服版本与日服版本不同
- 台服看到的 49 个响应恰好都是小响应（`n=32` 表示「无额外数据」）
- 我们对 `declared` 的读取位置错了

**结论：必须重新抓一次响应，逐字节确认这个 u32 到底是什么。** 这条不解决，服务器独立加密就无从谈起。

### 2.2 AES 模式

| | 定义 |
|---|---|
| 台服 | **AES-128-CBC / PKCS7**，key 与 iv 都是 16 字节 |
| 本项目 | **AES-128-CTR**（`ks[i] = AES-128-ECB(key, IV12 ‖ BE32(ctr+i))`），197/200 匹配 |

这两种模式在数学上不可能同时成立——CBC 的输出依赖前一块密文，CTR 的输出只依赖计数器。

**可能的解释**（未验证）：
- 请求方向用 CTR，响应方向用 CBC
- 台服测的是另一个接口/另一层
- 我们 hook 的 `libnative+0x43B70` 是底层 AES 单块原语，CBC 和 CTR 都会调用它；我们看到的 `IV12‖ctr` 结构恰好长得像 CTR

**结论：优先级最高的待验证项。** 台服说 8/8 真实配对逐字节匹配、45155 种组合中唯一命中，这个证据强度很高。

### 2.3 密文头部 32 字节的构成

| | 定义 |
|---|---|
| 台服 | `[sid16(16) ‖ udid16(16)]`，然后才是 `rnd32` 和 `authKey` |
| 本项目 | 曾认为是「随机 nonce」，三次抓包全不同，与 key/IV 无关 |

**台服的解释更具体，且有推导链**：`sid16 = Hex2bin(请求头 SID)`（32 位 hex → 16 字节）。

如果成立，那 32 字节「随机头」其实是会话绑定数据，**这意味着响应不是完全无状态的，服务器必须知道请求的 sid16**。

**这一条如果成立，会直接推翻「服务器可以独立加密任意响应」的前提**——因为服务器必须知道客户端本次请求用的 sid16。

### 2.4 请求 key/iv 的派生

| | 定义 |
|---|---|
| 台服 | `key = MD5(sid16 ‖ HDR[32:52])`、`iv = MD5(udid16 ‖ HDR[32:52])` |
| 本项目 | 曾尝试 90 种标准 KDF（用 `GenRandomBytes(0x20)` 的输出当私钥做 X25519），全部失败 |

**台服的公式解释了为什么我们全失败**：我们用的不是 `sid16`，而是 `GenRandomBytes(0x20)` 的随机盐——那个东西根本不参与密钥派生。

`HDR[32:52]` 是 20 字节，与我们抓到的 `CommonHeader` 后 20 字节（证书指纹 `52C9B948725E8F79AC1E9195B458F6596911CD5C`）吻合。

**这个公式可以立即验证**：拿一个请求的 `sid16` + 那 20 字节指纹算 MD5，与 `[aes]` hook 抓到的 key 对比。**但目前缺 `sid16` 样本**（插件没记录 HTTP 头）。

## 三、只有台服有的（对我们有价值）

| 内容 | 价值 |
|---|---|
| `请求头 SID = MD5(UTF8(raw_sid + "u1v72NHqkB"))` | **盐值明文**，解释了 42 字符 raw sid 与 32 字符请求 SID 的关系 |
| `Certification.get_SessionId @ 0x186BD3960` 等 5 个机器码地址 | 可直接反汇编会话读写点 |
| `UpdateSessionID` 在 `sid` 为空时**没有保护分支** | 解释了我们遇到的「会话被清空」问题 |
| `CommonProcessOnResponded` 内部还有一份内联会话写入 | 说明拦 setter 不够，还要拦响应处理 |
| 218 是**上游透传**，不是本地产生 | 排除了「本地逻辑错误」的可能 |
| 错误响应也必须写会话标记 | 否则错误后紧跟的一次请求就 218 |
| `MsgPackTree` 的 Read→Write **不是无损往返** | float32→float64、uint64 变负、重复键折叠 |
| `dotnet build` 增量构建「假成功」的判据 | 与我们的 `cargo` 构建坑类似 |

## 四、只有我们有的（对方报告没覆盖）

| 内容 | 说明 |
|---|---|
| **`GenRandomBytes(0x20)` 是明文随机盐** | 通过反编译 `CompressRequest` 确认，它被拼进明文头部，不参与密钥派生 |
| **`CommonHeader` 是编译期常量** | `RuntimeHelpers.InitializeArray` 从静态数据填充 52 字节，不参与运行时计算 |
| **`CompressRequest` 全链路 = Concat → LZ4 → base64** | 无 AES、无 ECDH |
| **`HttpManager.CompressFunc` 实证指向 `CompressRequest` 自己** | 用 hook 拿到 `method_ptr` 验证过 |
| **`WWWRequest.Post` 是纯 UnityWebRequest** | 无加密 |
| **`libnative+0x10F0` 是 LZ4 压缩** | Ghidra 反编译，2677 字节，无加密调用 |
| **TLS 层是标准 TLS 1.3** | `openssl s_client` 实测：X25519MLKEM768 + AES-256-GCM |
| **`0x14F60` 的 `ctx+0x180` 是 AES 输入块** | 反汇编确认 `lea rdx,[rcx+0x180]` 后接 `call 0x43b70` |
| **AES 分派的 key 在 `[ctx+0x50]+0x10`** | 176 字节扩展密钥表自洽验证通过 |

## 五、下一步验证计划（按优先级）

### 第 1 步：确认 LE32 字段（最高优先级，15 分钟）

抓一个真实响应的**原始字节**，逐字节确认：
- 如果 `u32` 恒为 32 → 台服对，它是头长度
- 如果 `u32` 等于明文长度 → 我们对

### 第 2 步：验证 KDF 公式（30 分钟）

需要样本：`sid16`（请求密文头前 16 字节）、`udid16`、`HDR[32:52]`、以及 `[aes]` hook 抓到的 key。

然后算 `MD5(sid16 ‖ HDR[32:52])` 看是否等于 key。

**这一步能一次性确认台服公式在日服是否成立。**

### 第 3 步：确认 AES 模式（1 小时）

用已知的 `(key, iv, 明文, 密文)` 四元组，同时试 CBC 和 CTR，看哪个对得上。

### 第 4 步：如果是 CBC，重新解释 `IV12‖ctr`

我们在 `ctx+0x180` 看到的 `12 字节 IV + 4 字节递增计数器` 结构，如果是 CBC，那就不是计数器，而是别的含义——需要重新解析。

## 六、结论

台服报告**信息量远高于我们目前的进展**，尤其是：

1. `key/iv` 的派生公式有实测支撑（8/8 逐字节 + 45155 组合唯一命中）
2. `sid16` 就是密文头前 16 字节这个结构关系
3. 会话三种表示的区分（raw sid / 请求头 SID / sid16）解释了大量我们遇到的矛盾

**但有两处硬矛盾必须解决**：LE32 字段的含义、AES 的模式。在这两点确认之前，不能按台服的结论动手实现。

**同时注意**：台服报告是针对**本地服务端**（拦截+回放）写的，我们的目标是**服务器独立加密**。即使 KDF 公式成立，还需要确认「服务器能否独立算出 key」——如果 key 依赖 `sid16`，而 `sid16` 又是客户端每次请求随机生成的，那服务器就必须先拿到它。
