# libnative 编解码器翻译进度

目标：把 `libnative.dll` 的压缩/解压链路完整翻译成 Python，实现离线解码 API body。

## 重大发现（2026-10-24）

**这一整块是"多精度算术"，不是压缩算法。**

证据：
- `0x45900` / `0x45c10` / `0x45d10` 是 limb 数组的分配 / 拷贝 / 赋值（每 limb 8 字节 = 64 位，上限 10000 limbs）
- `0x74e60`（190 行）是 64×64→128 位乘法 + 进位链，`mulx` 的软件展开
- `0x75720`（85 行）是 XOR 奇偶校验（ECC），250/30 次重试
- `0x472f0`（1131 行）里**除法 0 次、取模 0 次**，但有 9 次 `calloc`、12 次 `memcpy`，常量 `0x2711`(10001)、`0x8000000000000000`

**影响**：Python 的 `int` 原生支持任意精度，底层那约 2,500 行（limb 管理、进位链、符号处理、多精度乘除）**全部不用翻译**。

| 项 | 原估 | 修正后 |
|---|---|---|
| 传递闭包总行数 | 3,746 | 3,746 |
| bignum 底层 | — | ~2,500 行（用 Python int 替代） |
| **真正要翻译的算法逻辑** | 3,746 | **~500 行** |

## 2026-10-24 深夜：链路完全打通，解密层仍未复现

### 决定性发现：底层是标准 LZ4

`0x173210`（被 `0x3180` 在输出前调用）是教科书式的 LZ4 block 解压器：

```c
bVar3 = *param_1;                 // token
uVar13 = bVar3 >> 4;              // 高 4 位 = literal 长度
if (uVar13 == 0xf) {              // 15 触发扩展
    do { bVar4 = *pbVar19++; uVar12 += bVar4; } while (bVar4 == 0xff);
    uVar13 = uVar12 + 0xf;
}
lVar14 = pbVar19 - param_2;       // offset
do { *param_2 = *(u64*)(lVar14 + param_2); param_2++; } while (param_2 < puVar20);
```

⇒ 完整链路是：

```
src payload
  → 解密层（PCG + 16 项 S-box + 48 字节节点的树运算）
  → LZ4 block 压缩数据
  → 0x173210 标准 LZ4 解压
  → dst (msgpack)
```

这解释了此前所有 LZ4 库尝试失败的原因：payload 是加密的，必须先解密。

## 2026-10-25 突破：LZ4 输入已落盘并可被标准库解压

### 关键实证

hook `0x143210`（真正的 LZ4 block 解码器，VA `0x7ffa1b173210`）在**返回后**按 `ret`（消耗的输入字节数）落盘 `/lz4in/{n}.bin`：

```
lz4in/0.bin   361  →      526 字节   lz4.block 解压成功
lz4in/1.bin  199445 → 1200869 字节  lz4.block 解压成功
lz4in/2.bin  14865  →   51413 字节  lz4.block 解压成功
```

三个文件开头均为 `f2 65 83 ad 72 65 73 70 6f 6e 73 65 5f 63 6f 64 65`：
`f2` = token（litlen 15 走扩展），`65` = 扩展字节（15+0x65 = 116），
随后 116 字节字面量就是 msgpack 明文。

**⇒ 离线解压已通**：拿到 `lz4in` 后纯 Python `lz4.block.decompress(data, uncompressed_size=declared)` 即可。

### 仍未复刻：`src[36:]` → `lz4in`

| 项 | 值 |
|---|---|
| 头长度 | 固定 **36**（`len(src) - len(lz4in)` 恒等于 36） |
| `src[0:4]` | 明文长度 LE |
| `src[4:36]` | 32 字节密钥材料，每请求不同 |
| `src[36:]` | 加密后的 LZ4 流（长度与 `lz4in` 相同） |
| keystream | `lz4in XOR src[36:]` |

keystream 前 256 字节两个样本只有 0.8% 相同 → **有状态、每请求不同**。

### 已排除

| 假设 | 命中率 |

| AES-256-CTR（key = `src[4:36]`，nonce=0） | 1.1%（随机） |
| ChaCha20（同上） | 0.6%（随机） |

### `e180` 抓不到是因为被内联

`0x3180` 里 `0x38f3 call 0xed20` / `0x393c call 0xe180` 成对出现，受 `r15` 与 `[rbp+0x18]` 控制，实测都零调用；但 `dst+declared` 在进入时全 0、LZ4 调用时已有正确数据。

对 `0x3180` 全 958 条指令逐段核查完毕：

- 所有 call：`0x8fa0`(ctx init)、`0x1c000`(算法9)、`0x97af0`(calloc)、`0x15ac0`(大整数扩容)、
  `0x90d80`(free)、`0x9170`/`0x9080`(大整数释放)、`0x16600`(cmp)、`0x16030`(bitlen)、
  `0xf910`/`0xf210`(大整数除法)、`0xed20`/`0xe180`(曲线编解码)、`0x2bc8c0`(**memset**)、
  `0x2bcc80`(**identity**)、`0x135d0`(MD5 block ×6)、`0x143e0`(MD5 init)、`0x154f0`(哈希校验)、
  `0x143210`(LZ4)
- 字节写入只有 `0x3abf–0x3c57` 那组 `0x300↔0x31f` 成对的**栈上 32 字节反序**

**没有 memcpy、没有搬运循环** → 填充 `dst+declared` 的只能是内联后的 `e180`。
